# リリース設計の判断記録

このリポジトリのリリース基盤を「**なぜそうしたか**」で記録する。手順（どう操作するか）は
[release-process.md](release-process.md)、実体は [build.yml](../.github/workflows/build.yml) と
[/release スキル](../.claude/skills/release/SKILL.md)。ここはその背後にある判断と理由を残し、
別プラグインでも同じ考え方を再利用できるようにする。

## 背景

- 個人利用に近い Obsidian プラグイン。対外公開を厳密に運用するフェーズではない。
- やりたかったこと: GitHub Release を起点にビルドし、成果物が**改ざんされていないことを示せる**状態にする。
- 制約として重視したこと: **秘密情報（鍵・トークン）を持ちたくない**／**取り消せる安心感**を残したい／
  運用の手間と作り込みは最小にしたい。

以下の判断はすべてこの優先度から導かれている。

## 判断一覧

| # | 決定 | 一言で |
|---|---|---|
| 1 | リリースのトリガはタグ push のみ | バンプ忘れを構造的に防ぐ |
| 2 | バージョンの真実源は `package.json` | 編集点を1つに集約 |
| 3 | `versions.json` は固定1行 | 厳密な minAppVersion 運用をしない |
| 4 | 改ざん対策は keyless 署名 + checksums | 秘密鍵を持たない |
| 5 | Immutable Releases はオフ | 取り消せる状態を優先 |
| 6 | Release は draft・手動 Publish | 自動で公開しない |
| 7 | 多層 CI ガードを置かない | 手順固定で整合を担保 |
| 8 | リリースノートは GitHub 自動生成 | 文章を自前で書かない |
| 9 | Action は SHA ピン留め・Node は `.node-version` で固定 | 実行系を再現可能にする |
| 10 | `/release` スキルは upstream 無しで停止 | スキルが暗黙にリモートを作らない |
| 11 | npm は `min-release-age=7` | 公開直後のバージョンを掴まない |
| 12 | install スクリプトは `allowScripts` で明示許可 | 未レビューの実行を残さない |

---

### 1. リリースのトリガはタグ push のみ

- **決定**: ワークフローは `v*` タグの push でのみ起動する。タグを作る正規手段は `npm version` だけ。
- **理由**: 「リリースする唯一の方法 = タグ push」「タグを作る唯一の手段 = `npm version`」とすると、
  **バンプを忘れる＝タグが無い＝リリースが発生しない**。古い版がサイレントに公開される事故が原理的に起きない。
  忘れた場合の症状は「コードを push したのに何も公開されない」という目に見える形になる。
- **検討した代替案**: main への push を起点に毎回ドラフトを作る方式。常に最新ドラフトが用意される利点はあるが、
  「バンプ忘れ」は publish 時の人手チェックに頼ることになる。
- **トレードオフ**: リリースは必ず `npm version` を通す必要がある（手で任意のタグを切る運用はしない前提）。

### 2. バージョンの真実源(SSoT)は `package.json`

- **決定**: 版番号は `package.json` だけで管理し、`npm version` でバンプする。`version` フックで
  [`scripts/version-bump.mjs`](../scripts/version-bump.mjs) が `manifest.json` に同期する。
- **理由**: Obsidian では `manifest.json` / `versions.json` は実行時参照できず、版番号が物理的に書き込まれて
  いる必要がある。そこで「手で編集するのは1か所」「他は自動同期」を満たす形にした。`npm version` は
  バンプ・コミット・タグを1コマンドで原子的に行え、Obsidian 公式サンプルの慣習とも一致する。
- **検討した代替案**:
  - `manifest.json` を SSoT にする → `npm version` の恩恵を失い、独自スクリプトが必要。
  - ビルド時に版番号を `manifest.json` へ注入する → コミット済み manifest が実版と食い違い、
    `versions.json` の累積更新も賄えない。
- **トレードオフ**: `package.json`（Obsidian は読まない）も版を持つが、npm ネイティブな真実源として割り切る。

### 3. `versions.json` は固定1行

- **決定**: `{"0.0.1": "1.0.0"}` の1行で据え置き、リリースごとに更新しない。`minAppVersion` も `1.0.0` 固定。
- **理由**: `versions.json` は「最新版が動かない古いアプリに代わりに配る旧版」を探すための表。
  常に最新の Obsidian で使い `minAppVersion` を上げない運用では、Obsidian は `manifest.json` の
  `minAppVersion` にフォールバックするため、この表が参照される場面が来ない。
- **検討した代替案**: バンプ時に `{version: minAppVersion}` を追記する公式同様の厳密運用。配布を本格化したら移行可能。
- **トレードオフ**: 将来 `minAppVersion` を引き上げて複数版を配るなら、この方針は見直しが必要。

### 4. 改ざん対策は keyless 署名 + checksums

- **決定**: `actions/attest-build-provenance` による SLSA build provenance（Sigstore の keyless 署名）と、
  SHA-256 checksums をアセットに付ける。
- **理由**: keyless 署名は GitHub OIDC で実行時に使い捨ての証明書を発行するため、**保存する秘密鍵・API キーが
  存在しない**。漏洩しうる秘密を持たずに「CI が作った・改ざんされていない」ことを暗号的に証明できる。
  公開リポジトリなら追加設定なしで無料で動く。
- **検討した代替案**: マーケットプレイス署名のように秘密鍵を Secrets に置く方式 → 鍵管理・漏洩リスクを抱えるため却下。
- **トレードオフ**: 非公開リポジトリでは attestation の保存がプラン条件に絡む場合がある（その場合でも鍵管理は不要で、
  最悪 checksums だけでも改ざん検知は成立する）。

### 5. Immutable Releases はオフ

- **決定**: GitHub の Immutable Releases は当面有効化しない。
- **理由**: 改ざん「防止（ロック）」と「取り消し不可」は表裏一体。今は誤リリースをやり直せる安心感を優先する。
  改ざんは #4 の署名 + checksums で**検知**できるので、ロックしなくても正当性は担保できる。
- **トレードオフ**: 公開後でもアセットを差し替えられる＝「公開＝確定」の強制力は無い。運用が固まったら有効化に移行可能。

### 6. Release は draft・手動 Publish

- **決定**: ワークフローは `--draft` で Release を作り、自動公開しない。Publish は人が UI で行う。
- **理由**: 自動化を「ドラフト生成まで」で止め、取り消しにくい公開を人手ゲートの後ろに置く。
  自動で公開されるのはタグだけで、それも削除可能。
- **トレードオフ**: 最後に1手（Publish）が残るが、安全性と引き換えに許容する。

### 7. 多層 CI ガードを置かない

- **決定**: 「タグと各ファイルの版が一致するか」等の検証ジョブは設けない。
- **理由**: リリースを `npm version` 経由に固定すれば、タグは `package.json` の値から作られ、`manifest.json` も
  フックで同期されるため、整合は**構造的に**保たれる。ガードは外したのではなく、手順固定により不要になった。
  個人リポジトリでは「強制ゲート」より「正しい手順を1本化」の方が軽くて十分。
- **トレードオフ**: 手順（`/release` スキル / 手動手順）を通さず手で操作すると素通りする。そこは #10 とドキュメントで補う。

### 8. リリースノートは GitHub 自動生成

- **決定**: `gh release create --generate-notes` で "What's Changed" を生成する。AI や人手で本文を書かない。
- **理由**: ノート作成を GitHub に委ね、冗長な自動生成文や手書きの手間を避ける。
- **トレードオフ**: 自動ノートはマージ済み PR ベースのため、直接コミット中心だと内容は薄くなる（compare リンク中心）。
  必要なら Publish 前に手で加筆する。

### 9. Action は SHA ピン留め・Node は `.node-version` で固定

- **決定**: 全 GitHub Action をフルコミット SHA でピン留めし、[pinact.yml](../.github/workflows/pinact.yml) で
  検証を強制する。Node は [.node-version](../.node-version) に LTS の特定パッチ（24.19.0）を書き、
  ローカル（mise）と CI（setup-node の `node-version-file`）の両方がこの1ファイルを読む。
- **理由**: タグ（可動）ではなく SHA で固定することで、再タグ付けされた悪性アクションが書き込み権限付きで
  動くのを防ぐ。Node も同じ考え方で、ローカルと CI の実行系を一致させて再現可能にする。以前は `lts/*` で
  実行時に最新 LTS を解決していたが、これは Node 26 が LTS 化する 2026-10-28 に黙ってメジャーが飛ぶ。
  **LTS 追従自体はやめないが、メジャーを跨ぐタイミングは人の判断に戻す**、というのが今回の決定。
- **`.node-version` を置き場所に選んだ理由**: mise・setup-node・Renovate（nodenv マネージャ）の3者が
  そのまま読める唯一の形式だから。`mise.toml` の `[tools]` に書くと setup-node が読めず（`node-version-file`
  の mise.toml 対応は未リリース）、CI 側に版番号を再掲することになる。逆に mise は既定で `.node-version` を
  読まないため、[mise.toml](../mise.toml) では `idiomatic_version_file_enable_tools` で node だけ有効化している。
- **元の懸念への回答**: 「固定メジャーはランナーから外れた時に壊れる」という当初の懸念は、EOL が 2028-04-30 の
  LTS を選ぶ限り当面顕在化しない。
- **トレードオフ**: Action 更新時は SHA を貼り直す手間がある（pinact が未ピンを検知する）。Node もパッチ追従が
  手動になる（Renovate を入れれば `.node-version` と Action の SHA をまとめて自動 PR にできる）。Node 24 は
  2026-10-20 に maintenance 入りするため、そこが次の見直し点。Action 自体の Node ランタイム世代は別問題で、
  古いと deprecation 警告が出る → Node24 世代の版へ更新して解消した。

### 10. `/release` スキルは upstream 無しで停止

- **決定**: スキルは対象ブランチに upstream が無ければ、バンプもタグ作成もせずに停止する。
- **理由**: upstream が無いと `git push --follow-tags` が失敗してタグも飛ばない。スキルが勝手に
  `git push -u` してリモートブランチを作る（暗黙の外向き操作）のは避け、ユーザーに明示させる。
- **トレードオフ**: 初回は手動で `git push -u origin <branch>` が要る。これは意図的な明示ステップ。

### 11. npm は `min-release-age=7`

- **決定**: [.npmrc](../.npmrc) に `min-release-age=7` を置き、公開から7日経っていないバージョンは
  インストールしない。
- **理由**: 近年の npm 供給網攻撃は、乗っ取ったアカウントから悪性バージョンを公開し、それを踏んだ環境から
  さらに広がる形が多い。多くは数日のうちに検知・削除されるため、**待つだけ**でリスクがかなり下がる。
  秘密を持たない（#4）のと同じで、運用の手間を増やさずに効く対策を選ぶ方針に沿う。
- **7日という数字**: このリポジトリのメンテナンス頻度から決めた。毎日触るなら短くする余地があるが、
  更新が散発的なので依存の鮮度より「1週間分の検知期間」を優先する。
- **影響範囲**: 効くのは依存の追加・更新時の解決だけ。CI の `npm ci` はロックファイル通りに入れるため
  影響しない。
- **トレードオフ**: 緊急パッチの取り込みが最大7日遅れる。`npm audit fix` が7日以内の修正版を入れようとすると、
  npm は脆弱なまま警告して非ゼロ終了する。急ぐ場合は `min-release-age-exclude` に対象を一時追加して回避する。

### 12. install スクリプトは `allowScripts` で明示許可

- **決定**: [package.json](../package.json) の `allowScripts` で、依存の install 時ライフサイクルスクリプト
  （`preinstall` / `install` / `postinstall` など）を明示的に許可・拒否する。esbuild と fsevents は
  **バージョン付き**（`esbuild@0.21.5`）で許可し、svelte-preprocess は拒否した。
- **理由**: install スクリプトは `npm install` しただけで任意のコードが走る経路で、供給網攻撃の主要な入口。
  npm は現状「実行はするが未レビューの一覧を警告に出す」段階だが、将来のリリースで未レビューのスクリプトは
  ブロックされる。先に方針を決めておけば、その時に慌てて判断せずに済む。
- **バージョン付きで許可する理由**: 名前だけの許可（`pkg: true`）だと、後から入った別バージョンのスクリプトも
  自動的に許可される。ピンしておけば版が上がるたびに人が見直すことになる。#11 と同じく**自動では通さない**を選ぶ。
- **svelte-preprocess を拒否した理由**: postinstall の中身が注意書きを echo するだけで、実行される必要がない。
  「必要なものだけ許可する」を実際に適用した例。拒否しても導入・ビルドに影響はない（確認済み）。
- **トレードオフ**: esbuild などを更新するたびに `npm approve-scripts` での再承認が要る。これは #11 の
  待機期間と同じで、意図的に増やした人手のゲート。
